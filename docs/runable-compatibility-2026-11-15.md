# Runable compatibility — read-only research, 2026-11-15 UTC

## Conclusion

The likely intended service is **https://runable.com**, an AI business/work agent. It has an official externally accessible MCP server. There is enough primary documentation to prepare a bounded, authenticated handoff; there is **not enough evidence to claim a live Store Ops / Content Creator / POD integration**. No account was connected, task launched, credits consumed or repository code changed in this research. Keep existing Hub orchestration and deployment ownership.

Do not conflate this with `runablejs.com`, `runnable.cloud`, Runbear or Runway; those search results describe other products. No claim is made that `runable.pro` belongs to the same operator.

## API, webhook and auth unknowns

No public primary reference was found for a general Runable REST developer API with API-key provisioning, OpenAPI schemas, inbound webhook triggers, webhook signatures, outgoing task callbacks, customer-defined connector registration, or service-account auth. Terms referring to “APIs” do not establish callable endpoints. Do not reverse engineer private app endpoints or borrow API paths from similarly named products. The documented MCP endpoint is the first supported integration candidate, pending user-owned account connection and schema discovery.

Runable login consent does not authenticate to Raven Sharp, Etsy, MyDesigns or Metricool. Those connections and owner/tenant permissions remain distinct. No Runable tool is currently available in this agent's active tools. No new plugin/account installation was requested as part of this bounded research.

## Existing source compatibility — observed, not rewritten

The following are source observations and engineering requirements, **not vendor promises**:

- **Store Ops**: current inspected Worker in `/workspace/store-ops-fix` has encrypted sessions, Etsy OAuth/PKCE, HttpOnly Secure SameSite=Lax cookies, exact same-origin mutation checks and CSRF validation. Browser form mutations from `runable.com` are therefore expected to be blocked. Preserve these controls. A cross-site error should be fixed at the canonical same-origin app/proxy path first; globally allowing arbitrary origins or sharing sessions would weaken the existing boundary. Inspect `src/security.js`, `src/app.js`, agent routes and existing `docs/manager-hub-integration-contract.md`. Authenticated agent routes, if configured, are the correct candidate for a scoped server-side adapter; verify their actual schema and gates before Runable use.
- **Content Creator**: inspected `backend/server.py` accepts app cookies or Authorization bearer JWT and restricts credentialed browser CORS to configured origins/Raven Sharp subdomains. `backend/app_v2.py` already has `/api/v2/render/social-image`, `/render/carousel`, video compose/status, narration and one-time Book handoff. Keep those existing capabilities. A Runable handoff can return an approved brief or finished public asset URL; it must not silently call paid animation/narration models. Bearer support is not a long-lived service-account/refresh contract. Browser CORS changes are irrelevant to authenticated server-to-server requests and should not be used to fix missing service auth.
- **POD**: inspected `/workspace/pod-full/backend/server.py` uses FastAPI/Mongo, app JWT/cookie auth, credentialed CORS, Etsy OAuth and Runware operations. No MyDesigns integration was established by this research. Preserve transparent print files and original resolution; require preflight dimensions, colour/alpha checks, safe mockups, provider SKU/variant/country costs and fulfilment cash evidence. A Runable image/video export is not a print-readiness or margin pass.
- **Ad Manager/distribution**: use existing approval + durable publication records; campaign generation and publishing remain separate stages. Never treat a Runable completed task or file download as an active Etsy listing, public social post or conversion. Media URL and actual provider receipt must be recorded independently.

## Recommended minimal handoff contract (engineering inference)

Runable is the intended workflow owner once its supported connection is verified. Preserve existing schedules until an explicit cutover; avoid duplicate orchestration or new Hub work. If the user intends actual Runable execution, first connect the documented MCP service through supported sign-in, inspect tools/scope and verify a read-only list/status operation. Then establish per-account free credits and zero-spend behaviour before any generative task. Do not assume the external MCP connection imports the user's ChatGPT connector credentials.

Each requested task should carry a stable job/campaign ID, tenant/owner, desired output, original input asset references + SHA-256 hashes, output MIME/dimensions, approved source/cost bounds and explicit `draft_only`/`publish_not_authorised` intent. These are our proposed payload fields, **not known Runable tool arguments**. Translate only after discovering actual schemas.

Ingest a result as an untrusted deliverable: capture Runable task ID/status/time, download through the documented mechanism, verify MIME/content/checksum/size and product claims, place it through existing Store Ops/POD/content QA gates, and persist both provenance and failure state. Never store tokens in artifacts. Do not auto-retry a paid or externally mutating job after a timeout until status is reconciled. Keep original files and a reversible source commit.

Before claiming compatibility, test one free bounded draft task and file round-trip for the chosen output; then an authenticated staging request into the existing app; then duplicate/timeout/expired-auth handling and cross-tenant denial. Only afterwards exercise existing reviewed-draft upload or publication controls with the authorised shop. No such tests occurred in this research.

## Precise remaining blockers

1. User confirmed Runable; the researched official service is `runable.com`. Actual account access is still unavailable.
2. Existing Runable account/MCP connection and actual schemas/scopes/credit settings unavailable.
3. No verified native Etsy/MyDesigns/Metricool/custom Raven Sharp connector, REST API or webhook contract.
4. No live file round-trip or size/MIME acceptance test; docs host retrieval failed.
5. Existing app integration credentials, owner-scoped auth/refresh, draft attachments and callback/receipt behaviour need their own test; a migration import must not replace them.

No workstream needs to wait for Runable to repair its own same-origin routes, produce original files or pass existing QA. The useful next step is the existing Store Ops cross-site fix followed by a bounded supported adapter only once Runable's actual connection surface is known.
